# `releases list/delete`, better update notice, upload retry

## Objective
Three independent, unrelated features authorized by the user in one go ("hazlos"): non-interactive `relio releases list`/`delete`, a self-update notice that tells the user the right upgrade command instead of just "there's a new version," and retry/progress for `relio image`'s litterbox/catbox uploads.

## Why
Remaining items from the TUI gap analysis + the deferred self-update decision, both from earlier this session. Self-update auto-install was explicitly rejected (user, AskUserQuestion): relio ships via Homebrew, so replacing its own binary would fight `brew upgrade` — chose "improve the notice only" instead.

## Scope & mapping (from delegated codegraph-based exploration this session)

### T1 — `relio releases list` / `relio releases delete <version>`
- `internal/releases.Run` (the Bubbletea TUI reachable from the interactive menu's "View releases") **already does this interactively**: lists local tags (`repo.Tags()`, `internal/gitrepo/gitrepo.go:87`) with their CHANGELOG.md subject lines, and `d`/`x` + confirm deletes the **local tag only** (`gitrepo.DeleteTag`, `gitrepo.go:128`) plus the matching `## [version]` changelog section (`changelog.RemoveSection`) — no remote/GitHub Release interaction at all, and it's currently untested (no test file found for `internal/releases`).
- `cmd/releases.go` (`newReleasesCmd`) only registers `edit` today — no non-interactive `list`/`delete`.
- **No GitHub API List/Get/Delete exists anywhere in `internal/ghrelease`** — only `Create` (`ghrelease.go:66`, POST) and `AuthenticatedUser` (GET) exist as auth/HTTP patterns to model from.
- **Scope decision (orchestrator, not asked — matches existing established behavior rather than inventing new scope):** `relio releases delete <version>` mirrors the TUI exactly — local tag + changelog section only, NOT the remote GitHub Release or a pushed tag. Deleting a *published* GitHub Release is a materially bigger, riskier, higher-consequence feature (public-facing, needs its own careful design/confirmation/token-scope story) that nothing in this codebase does today; scoping to what the TUI already does keeps CLI and TUI behavior consistent and avoids scope creep into an unrequested feature. Document this as an explicit limitation in the command's help text and docs.
- `relio releases list`: non-interactive dump of the same data source the TUI uses (`repo.Tags()`), plain text/table, no GitHub API call needed.
- `relio releases delete <version>`: needs a confirmation prompt (or `--yes`, matching `relio undo`'s existing pattern — see `cmd/undo.go`) since it's destructive; reuses `gitrepo.DeleteTag` + `changelog.RemoveSection`, the same building blocks the TUI already uses (don't reimplement, extract if needed into a shared internal helper both the TUI and the new CLI command call).
- Test seams: `cmd/releases_test.go` already has a real-temp-git-repo pattern (`newStatusRepo`-style) to reuse.

### T2 — Self-update notice improvement (NOT auto-install)
- `update.Available(current)` (`internal/update/update.go:61`) already does the version-check (24h-cached, background-refreshed, respects `RELIO_NO_UPDATE_CHECK`/`CI`) — unchanged. Only the **notice text** changes.
- **No installation-source signal exists anywhere in the codebase today** — this is new. `.goreleaser.yaml` only injects `version`/`commit`/`date` via ldflags (`cmd/root.go:34-36`), no channel/source field.
- Add a new `InstallHint()`-style function (package TBD by the writer — likely `internal/update`) that checks `os.Executable()`'s resolved path for a `Cellar`/`homebrew`/`linuxbrew` substring (the standard heuristic for "this binary came from a Homebrew install") and returns the right upgrade command: `brew upgrade relio` (or `brew update && brew upgrade relio`) for a brew install, otherwise a generic pointer at the install docs (`docs/install.md`) for a manual install.
- Wire this into wherever the notice is currently rendered: `cmd/version.go:27` (TTY-only, non-interactive) and `internal/ui/ui.go`'s `Footer` (`ui.go:356`, used by the interactive menu via `cmd/root.go:197`).

### T3 — Upload retry/progress (`internal/upload`, used by `relio image`)
- `internal/upload/upload.go`: confirmed one flat `45 * time.Second` timeout (`upload.go:19`), zero retry/backoff, tries litterbox then catbox each exactly once (`Upload()`, `upload.go:29`), silent until success/failure (`post()`, `upload.go:56`, prints nothing).
- `litterbox`/`catbox` are `const`, not overridable `var`s (unlike `ghrelease.APIBase`) — must become vars for `httptest.Server`-based retry tests, matching that existing precedent.
- Reusable pattern for cancellable/testable retry sleep: `internal/ghrelease/deviceflow.go`'s `PollForToken` (`deviceflow.go:107-139`, `time.NewTimer` selected against `ctx.Done()`) — copy this shape, not `time.Sleep`.
- No spinner/progress primitive exists in `internal/ui`; closest precedent is `authLogin`'s one static "waiting..." line (`cmd/auth.go:79`, `AuthLoginWaiting` i18n key) — match that level of simplicity (a printed "retrying (attempt N/3)..." line is enough, no animated spinner needed).
- Caller: `cmd/image.go` prints only before/after the call (success ~`image.go:243`, failure ~`image.go:233`) — thread progress lines through the same `io.Writer` it already uses.

## Follow-up fix (RDD 4-lens review, reliability lens, CRITICAL R4-upload-retry-latency — commit pending)
The combined T1+T2+T3 review's reliability lens flagged `internal/upload`'s new retry logic: `Upload` was called from `cmd/image.go` with `context.Background()` (no deadline), so `maxAttempts=3` at up to 45s per attempt, across 2 hosts, could hang up to ~4.7 minutes with nothing to stop it. Two compounding bugs: (1) a progress-line write failure aborted the whole retry loop instead of being treated as cosmetic; (2) retrying a non-idempotent POST risks a duplicate upload if a response is lost after the server already stored the file.

Fixed with TDD (orchestrator, direct):
1. **Bounded total time**: added `overallTimeout` (90s default, package var for tests) — `Upload` now wraps its own context with `context.WithTimeout(ctx, overallTimeout)` regardless of what the caller passes, so it self-bounds even against `context.Background()`. A caller-supplied shorter deadline still wins (`context.WithTimeout` always honours the earlier of the two — verified by `TestUploadCallerDeadlineShorterThanOverallTimeoutWins`). New tests: `TestUploadBoundsTotalTimeEvenWithBackgroundContext`, `TestUploadCallerDeadlineShorterThanOverallTimeoutWins`.
2. **Progress-write failure no longer aborts retry**: the `fmt.Fprintln(progress, ...)` error is now deliberately discarded (`_, _ = ...`) instead of returned. New test: `TestUploadProgressWriteFailureDoesNotAbortRetry` (a writer that always errors; verifies the retry still completes and succeeds).
3. **Duplicate-upload risk — accepted tradeoff, not "fixed"**: considered restricting retries to transport-level errors only (never retry after any HTTP response was received), which would reduce this risk — but rejected it: the existing, already-tested retry behavior (`TestUploadRetriesOnFailureThenSucceeds`, `TestUploadFallsBackToCatboxAfterLitterboxExhausted`) deliberately retries on an ordinary non-2xx response (litterbox/catbox's own transient failures, the retry feature's main reason to exist), and refusing to retry after any response would silently break that intended, already-verified behavior. litterbox/catbox offer no idempotency key, so there's no clean primitive to close this gap without either breaking the feature's purpose or adding disproportionate complexity for a bounded correction. Documented as an explicit, accepted tradeoff in a code comment on `postWithRetry` instead of silently leaving it unexplained.

Re-entering review after fix #1 above surfaced two more CRITICAL findings from the readability lens (a provider session-limit transient failure also had to be retried on the reliability lens this round, unrelated to the findings):

1. **`R3-stale-model-after-delete`** (`internal/releases`): `Delete()`'s post-delete changelog `os.ReadFile` failure (any reason other than "file does not exist") was returned as a bare, unwrapped error — unlike the `WriteFile` failure, which was already wrapped in `*ChangelogWriteError`. `doDelete`'s error handling only calls `m.reload()` on that wrapped-error branch, so a bare read-failure error left the TUI's tag list stale: the git tag was already gone, but the browser kept showing it as present. Fixed by renaming `ChangelogWriteError` → `ChangelogError` (it's no longer just about writes) and wrapping the `ReadFile` failure in it too, so `doDelete`'s existing reload branch now correctly catches this case as well — one shared "the tag is gone but the changelog step failed, refresh state" signal instead of two inconsistent ones. Updated the pre-existing `TestDeleteReadErrorPropagatesRaw` (renamed `TestDeleteReadErrorWrapsError`, assertion inverted: it now confirms wrapping, since the original "must not be wrapped" assertion was itself the bug's spec) and `TestDeleteChangelogWriteFailureWrapsError`; added `TestDoDeleteReloadsAfterChangelogReadError` (model-level regression test proving `m.tags` is refreshed after this exact failure mode). RED confirmed (`undefined: ChangelogError` compile failure) before the fix.

2. **`R4-001`** (`internal/upload`): fix #1's `overallTimeout` was a single budget shared across *both* hosts and all retries — so a single slow-but-responsive host (the realistic degraded-service case retry exists for) could alone consume the entire 90s budget across 2-3 attempts, meaning the litterbox→catbox fallback the feature is documented to provide was never actually exercised; and `Upload` returned the bare `ctx.Err()` on timeout, discarding which host(s) were tried and why. Fixed by replacing the single `overallTimeout` with a `perHostTimeout` (60s default) applied independently per host via `context.WithTimeout(ctx, perHostTimeout)` inside the loop — litterbox exhausting its own budget no longer affects catbox's chance, and the `ctx.Err()` early-return now checks the *caller's* original context (not the per-host derived one), so a per-host timeout falls through to the normal `failed = append(...)` path and still names every host in the final error. New tests: `TestUploadPerHostBudgetDoesNotStarveFallback` (litterbox hangs past its budget; catbox still succeeds), `TestUploadBothHostsExhaustedNamesBothInError` (both hosts time out; error still names both). Renamed the existing `TestUploadBoundsTotalTimeEvenWithBackgroundContext`/`TestUploadCallerDeadlineShorterThanOverallTimeoutWins` tests' helper (`withOverallTimeout` → `withPerHostTimeout`) accordingly. Caught and fixed a self-inflicted test deadlock along the way (a `defer close(block)` ordered before `defer litterSrv.Close()` made `Close()` wait forever for a handler that could never return — defers run LIFO, so the close-the-channel defer had to be declared *after* the server's own `Close()` defer).
